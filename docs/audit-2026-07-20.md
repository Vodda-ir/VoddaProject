# گزارش ممیزی فنی و آمادگی production وُدّا

**تاریخ:** ۲۰ ژوئیهٔ ۲۰۲۶  
**مبنای بررسی:** شاخهٔ `main` مخزن `smae1993/VoddaProject` و اصلاحات شاخهٔ `agent/production-readiness`

## جمع‌بندی اجرایی

هستهٔ پروژه از یک MVP دارای چند ریسک بحرانی به نسخه‌ای قابل استقرار در محیط production تک-instance ارتقا یافت. مسیرهای اصلی Backend، Frontend و Flutter build/test شده‌اند و عملیات مالی داخلی اکنون transaction اتمیک، کنترل هم‌زمانی و integration test واقعی MySQL دارند.

این نتیجه به معنی آماده‌بودن کامل عرضهٔ تجاری نیست. دو قابلیت محصولی اصلی—درگاه پرداخت واقعی و تماس صوتی واقعی—به سرویس بیرونی، credential و تست end-to-end نیاز دارند و عمداً با پیاده‌سازی ساختگی جایگزین نشده‌اند.

## اصلاحات تکمیل‌شده

### ۱. تراکنش‌های مالی و هم‌زمانی

- ایجاد transaction boundary مستقل برای عملیات رزرو، escrow، refund، settlement، شارژ توسعه‌ای و برداشت.
- استفاده از row locking و update شرطی برای جلوگیری از موجودی منفی در درخواست‌های هم‌زمان.
- جلوگیری از refund، settlement و rejection تکراری بر اساس وضعیت قفل‌شدهٔ رکورد.
- ثبت درآمد ناخالص و کارمزد به‌صورت جداگانه تا جمع ledger با تغییر خالص کیف پول برابر باشد.
- تست واقعی MySQL برای رزرو/بازگشت وجه، برداشت ردشده، settlement و دو debit هم‌زمان.
- اجرای تست‌های Go با race detector در CI.

### ۲. امنیت احراز هویت وب

- حذف JWT از `localStorage` و cookie قابل‌خواندن با JavaScript.
- ایجاد BFF در Next.js با cookie امن `HttpOnly`، `Secure` در production و `SameSite=Lax`.
- حذف rewrite قدیمی `/api/v1` که امکان دورزدن BFF را فراهم می‌کرد.
- اعتبارسنجی session و role در middleware پیش از ورود به پنل‌های کاربر، استاد و مدیر.
- محدودسازی mutationهای BFF به same-origin برای کاهش CSRF و login CSRF.
- logout واقعی از طریق route سرور و پاک‌کردن cookie HttpOnly.

### ۳. امنیت HTTP و سوءاستفاده

- افزودن request ID و structured JSON access logging بدون body، token یا query value.
- افزودن security headerهای Backend و Frontend.
- افزودن body limit، multipart memory limit و timeoutهای HTTP.
- rate limit جداگانه برای OTP، verify، جستجو، mutationها، عملیات مالی و مدیر.
- تنظیم trusted proxyها از environment و عدم اعتماد عمومی به `X-Forwarded-For`.
- افزودن `/live` و `/ready`؛ readiness اتصال MySQL را بررسی می‌کند.

### ۴. آپلود و storage

- اعتبارسنجی byte-level MIME، پسوند و حجم آواتار.
- جلوگیری از `avatar_url` خارجی یا مسیر traversal در پروفایل.
- نام‌گذاری فایل سمت سرور و عدم directory listing.
- اجرای container Backend با کاربر non-root و volume پایدار `data/uploads`.

### ۵. چرخهٔ استاد و رزرو

- نمایش عمومی فقط برای استاد approved، verified، available و کاربر فعال.
- جلوگیری از دسترسی عمومی مستقیم به پروفایل pending/rejected با دانستن ID.
- حذف auto-create/auto-approve پروفایل استاد.
- اعتبارسنجی طول و محدودهٔ پروفایل، خدمت و برنامهٔ کاری.
- جلوگیری از self-approval خدمات؛ تغییر محتوای خدمت آن را به pending برمی‌گرداند.
- جلوگیری از بازه‌های کاری نامعتبر و هم‌پوشان.
- برداشت فقط برای استاد تأییدشده و فعال با شماره کارت/شبا معتبر.

### ۶. استقرار و عملیات

- محدودکردن پورت‌های Backend، Frontend و MySQL به localhost در Compose production.
- healthcheck وابسته به پورت environment و ترتیب شروع بر اساس service readiness.
- MySQL strict mode، کاربر اپلیکیشن جدا و volume پایدار.
- backup سازگار با transaction، فشرده‌سازی، SHA-256 و retention.
- restore محافظت‌شده با confirmation، checksum، safety backup و توقف کنترل‌شده سرویس‌ها.
- راهنمای عملیات، پایش، رخداد مالی و تمرین restore در `docs/production-runbook.md`.

### ۷. وابستگی‌ها و CI

- ارتقای Next.js، React و React DOM از نسخه‌های آسیب‌پذیر به patchهای امن پشتیبانی‌شده.
- بازتولید lockfile برای نصب reproducible با `npm ci`.
- CI چهار job مستقل:
  - Go + MySQL: format، vet، race/integration test و build
  - Next.js: install و build/type-check
  - Flutter: analyze و test
  - Deployment: shell syntax و Compose validation

## موانع باقی‌مانده پیش از عرضهٔ تجاری عمومی

### بحرانی و وابسته به سرویس بیرونی

1. **پرداخت واقعی:** request، redirect، callback و verify زرین‌پال، idempotency، تطبیق مبلغ و merchant، مدیریت callback تکراری و تست sandbox/production.
2. **تماس صوتی:** انتخاب provider، صدور token سمت سرور، lifecycle، reconnect، گزارش مدت و سیاست failure.
3. **چرخاندن secret پیامک:** کلیدی که قبلاً در تاریخچه بوده باید در پنل سرویس‌دهنده revoke/rotate شود؛ تغییر HEAD کافی نیست.

### قبل از بازکردن ترافیک واقعی

1. استقرار staging با secretهای واقعی و اجرای smoke test ورود، جستجو، رزرو، لغو و برداشت.
2. اجرای یک backup و restore کامل روی staging و reconciliation تعداد رکوردها و ledger.
3. پیکربندی TLS/reverse proxy و rate limit دوم در لایه edge.
4. فعال‌کردن monitoring/alerting بیرونی برای readiness، `5xx`، `429`، backup age و disk usage.

### برای scale چند-instance

1. انتقال avatar/audio به object storage مشترک.
2. rate limiter مشترک Redis یا reverse proxy.
3. session/revocation strategy مشترک در صورت نیاز به logout فوری همهٔ replicaها.

## معیار انتشار

انتشار تجاری پیشنهاد می‌شود وقتی:

- جریان پرداخت با sandbox و production و callback تکراری تست شده باشد.
- provider تماس صوتی روی شبکه‌های هدف تست شده باشد.
- secret قدیمی پیامک rotate شده باشد.
- CI شاخهٔ `main` سبز باشد.
- staging smoke test و restore drill موفق ثبت شده باشند.
- alertهای عملیاتی و backup خارج از همان سرور فعال باشند.

تا پیش از تکمیل پرداخت، endpoint شارژ مستقیم production عمداً بسته است؛ بنابراین هسته قابل استقرار است اما محصول تجاری بدون درگاه امکان تأمین موجودی واقعی کاربر را ندارد.
