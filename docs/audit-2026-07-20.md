# گزارش ممیزی فنی وُدّا

**تاریخ:** ۲۰ ژوئیهٔ ۲۰۲۶  
**مبنای بررسی:** شاخهٔ `main` مخزن `smae1993/VoddaProject`

## جمع‌بندی اجرایی

معماری کلی پروژه برای یک MVP قابل ادامه است و سه کلاینت اصلی روی یک API مشترک ساخته شده‌اند. با این حال، پیش از این ممیزی چند مورد بحرانی باعث می‌شد پروژه با وجود ظاهر تکمیل‌شده، برای production امن یا قابل اتکا نباشد. موارد بحرانی قابل اصلاح در همین مرحله برطرف شدند؛ موانعی که به سرویس بیرونی، تصمیم محصول یا بازطراحی دیتابیس نیاز دارند در بخش «کارهای باقی‌مانده» ثبت شده‌اند.

## اصلاحات انجام‌شده

### امنیت و پیکربندی

- حذف API key واقعی/شبه‌واقعی پیامک از مقدار پیش‌فرض کد.
- غیرفعال‌شدن پیش‌فرض OTP bypass، seed و شارژ مستقیم کیف پول.
- اعتبارسنجی اجباری تنظیمات production؛ سرویس با JWT ضعیف، SMS ناقص یا قابلیت‌های development بالا نمی‌آید.
- محدودشدن CORS در production به `CORS_ALLOWED_ORIGINS`.
- افزودن timeoutهای HTTP و محدودیت حافظهٔ multipart.
- برگشت خطای واقعی هنگام شکست ارسال SMS؛ دیگر پاسخ موفق جعلی داده نمی‌شود.
- جلوگیری از ورود کاربر غیرفعال.
- تعبیهٔ دیتابیس timezone در باینری و تعریف `APP_TIMEZONE`.

### پرداخت و کیف پول

- مسدودشدن `POST /wallet/charge` در production؛ این endpoint فقط با `DEV_WALLET_CHARGE_ENABLED=true` در محیط غیر production قابل استفاده است.
- افزودن جبران خطا برای ثبت تراکنش شارژ و برداشت.
- الزام حداقل یکی از شماره کارت یا شبا در درخواست برداشت.
- اصلاح نمایش مثبت درآمد کارمزد در داشبورد مدیر.

### رزرو و جلسه

- رد رزرو برای استاد تأییدنشده/غیرفعال، خدمت غیرفعال، قیمت یا مدت نامعتبر و رزرو توسط خود استاد.
- رد زمان گذشته، زمان بیش از شش ماه آینده و یادداشت بیش از ظرفیت مدل.
- کنترل قرارگرفتن جلسه داخل ساعات کاری استاد با timezone مشخص.
- جلوگیری از تداخل جلسه برای استاد و قرآن‌آموز.
- جلوگیری از پذیرش درخواست منقضی و اتمام جلسه پیش از پایان زمان آن.
- افزودن مسیرهای جبران برای خطاهای رزرو وجه و بازگشت وجه.

### وب Next.js

- یکسان‌سازی مدل `WorkTime` با JSON واقعی بک‌اند (`from/to` به‌جای `start/end`).
- اصلاح تبدیل روز هفتهٔ وُدّا با `Date.getDay()` و انتخاب نزدیک‌ترین زمان آینده.
- حذف روزهای تکراری، reset صحیح انتخاب‌ها و نمایش تاریخ کامل جلسه.
- تکمیل payload ثبت‌نام استاد شامل bio، شهر و قیمت.
- حذف موفقیت جعلی فرم تماس و اطلاعات تماس ساختگی؛ فرم اکنون برنامهٔ ایمیل را با متن آماده باز می‌کند.
- اصلاح layout موبایل پنل‌های کاربر، استاد و مدیر.
- نمایش لینک پنل‌ها بر اساس نقش واقعی برگشتی از API.
- حذف متدها و تست‌های stale مربوط به follow/unfollow که endpoint سروری نداشتند.

### نگهداری پروژه

- حذف فایل اتفاقی `todo.md` که حاوی prompt بود.
- اضافه‌شدن GitHub Actions برای build/test سه بخش.
- اصلاح README و چک‌لیست برای نمایش وضعیت واقعی، نه ادعای «کامل و تست‌شده».

## کارهای باقی‌مانده پیش از انتشار عمومی

### بحرانی

1. **درگاه پرداخت واقعی:** پیاده‌سازی request، redirect، callback و verify زرین‌پال، ثبت idempotency key و جلوگیری از callback تکراری. شارژ development نباید در production جایگزین این جریان شود.
2. **تراکنش دیتابیسی مالی:** رزرو، refund، settlement و withdrawal باید در یک transaction اتمیک GORM انجام شوند. جبران‌های فعلی ریسک را کم می‌کنند اما جای atomic transaction را نمی‌گیرند.
3. **تماس صوتی واقعی:** دکمه‌های شروع/ورود به جلسه هنوز provider واقعی، token server-side، lifecycle و گزارش مدت مکالمه ندارند.
4. **مدیریت secretها:** کلید پیامک قبلی باید در پنل sms.ir rotate شود؛ حذف از آخرین نسخهٔ کد، secret موجود در تاریخچهٔ Git را باطل نمی‌کند.

### زیاد

1. انتقال JWT از `localStorage` و cookie قابل‌خواندن با JavaScript به session امن HttpOnly یا BFF؛ middleware فعلی فقط وجود cookie را بررسی می‌کند و اعتبار/role را در edge تأیید نمی‌کند.
2. اعتبارسنجی MIME واقعی، محدودیت حجم قطعی، نام‌گذاری امن و انتقال avatar/audio به object storage.
3. rate limiting برای OTP، login، upload، search و endpointهای مالی در سطح Redis/reverse proxy.
4. افزودن unique/idempotency constraint برای settlement و refund تا retry باعث ثبت دوباره نشود.
5. طراحی و پیاده‌سازی کامل follow/favorite در backend، database، web و Flutter؛ فعلاً از قرارداد وب حذف شده است.
6. ساخت contact backend یا سرویس ticket/email قابل ردیابی؛ `mailto` فقط راهکار موقت و صادقانه است.

### متوسط

1. افزایش پوشش Go unit/integration، Flutter widget و end-to-end واقعی با MySQL.
2. افزودن test runner رسمی برای frontend؛ فایل تست قدیمی اجراشدنی نبود و حذف شد.
3. اضافه‌کردن observability: structured logging، request id، metrics، error tracking و alerting.
4. backup/restore تست‌شده، retention policy و runbook بازیابی.
5. pagination و سقف‌های سخت برای endpointهای لیستی و جستجوهای پرهزینه.
6. بازبینی accessibility، keyboard navigation و تست responsive روی دستگاه واقعی.
7. حذف داده‌های نمایشی مثل followers/reviews seed از محیط‌های staging/production و تعریف فرآیند migration داده.

## معیار آمادگی انتشار

انتشار عمومی زمانی پیشنهاد می‌شود که:

- پرداخت sandbox و production با callback تکراری و خطای شبکه تست شده باشد.
- رزرو، refund، settlement و withdrawal تست concurrency داشته باشند.
- تماس صوتی واقعی و سیاست failure/reconnect مشخص باشد.
- تمام jobهای CI سبز باشند و حداقل smoke test روی محیط staging انجام شود.
- secretهای قبلی rotate و secret scanning فعال شده باشد.
- backup و restore واقعی یک بار با موفقیت اجرا شده باشد.
